Persist Dag parse results a group at a time

The Dag processor now writes the files that finished parsing together in a single pass, rather
than one call per file. Everything a write does besides the Dags themselves is paid once per
group instead of once per file.

**What changed:**

- ``DagFileProcessorManager.persist_parsing_results`` is the seam for replacing the write. It is
  handed one group of ``FileParseResult`` at a time, together with the session to write on, and it
  sees every file that finished: one that defined no Dags, a callback-only run and a parse that
  failed all arrive, the last two carrying no ``parsing_result``. The team the file's bundle
  belongs to travels with it, so a replacement need not query the metadata database to find out.
- ``DagFileProcessorManager.persist_parsing_result`` and
  ``DagFileProcessorManager.handle_parsing_result``, which took one file at a time, are both
  deprecated and will be removed in Airflow 4.0. Overriding either still works until then, but
  parse results are persisted one file at a time and batching is skipped for the whole Dag
  processor.

- ``[dag_processor] max_dags_per_persistence_group`` bounds how many Dags one write may carry,
  defaulting to 32. A file is never split, so a single file defining more is still written in one
  go. Lower it if the Dag processor holding many rows in one transaction causes lock waits; set
  it to 1 to write one file at a time while keeping the new seam.

**Behaviour changes:**

- ``on_asset_created`` now reports the definition that is written. Where two files in one group
  define the same asset differently, writing a file at a time announced the first file's
  definition and then silently overwrote it, so the announcement disagreed with the row; a group
  coalesces the definitions before creating the row and announces what it wrote.

**Migration:**

- Move a ``persist_parsing_result`` or ``handle_parsing_result`` override to
  ``persist_parsing_results``, which receives a sequence of results and a session instead of one
  file's arguments. Check for ``parsing_result is None`` before reading a result's Dags: that is a
  callback-only run or a parse that failed, which the per-file hooks were never handed.
